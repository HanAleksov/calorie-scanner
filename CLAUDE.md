# Calorie Scanner — gotchas

- Backend and frontend are one FastAPI app: `backend/main.py` serves the API under `/api/*` and mounts `frontend/` as static files at `/`. There is no separate frontend server or build step.
- Vision calls go through `backend/vision.py`, model `claude-opus-5`, using `output_config.format` (json_schema) — the response is guaranteed valid JSON, no prompt-parsing fallback needed. If Anthropic ever deprecates `claude-opus-5`, only this one string needs to change.
- `ANTHROPIC_API_KEY` lives in `backend/.env` (gitignored). Never commit it.
- DB path and uploads dir are overridable via `CALORIE_DB_PATH` / `CALORIE_UPLOADS_DIR` env vars — used for Render's persistent disk and for test isolation. Don't hardcode paths in `db.py` or `main.py`.
- SQLite file and uploaded photos are gitignored — they're runtime data, not source.
- The service worker (`frontend/sw.js`) explicitly skips caching anything under `/api/` or `/uploads/` — cache-first there would show stale meal data or serve a 404 for a new photo. If you add new API routes, they're already excluded by prefix, no sw.js change needed.
- iOS does not read `manifest.json` for install — the `<meta name="apple-mobile-web-app-*">` tags and `apple-touch-icon` link in `index.html` are load-bearing for iOS home-screen install, not decorative.
- `est_grams` is `None`/`null` for manually-logged entries (no photo to estimate portions from) — the frontend must not assume it's always a number.
- **Bump `CACHE_NAME` in `frontend/sw.js` on every frontend change.** The service worker only re-checks its own script for byte changes; if `sw.js` is byte-identical to what's already installed, the browser never notices anything else changed. `app.js` and `style.css` are served network-first (fall back to cache offline) specifically so an installed PWA doesn't get stuck on stale UI — don't revert that to cache-first without a strong reason.
- `nutrition.py` and `meal_plan.py` are separate from `vision.py` on purpose — same Claude Opus 5 model, but text-only (no image), structured JSON output via `output_config.format`. `nutrition.py` is pure arithmetic (Mifflin-St Jeor), no API call.
- Profile fields can be `NULL` (nothing filled in yet) — `/api/goals/suggested` requires all of them and 400s otherwise; don't assume `db.get_profile()` returns a fully populated row.
- **Multi-user**: every table except `users` is keyed by `user_id`. The frontend sends it as an `X-User-Id` header on every request (see `apiFetch()` in `app.js`); `main.py`'s `current_user_id` dependency reads it and 401s if missing or unknown. There is no real session/token — the PIN (optional, 4 digits, sha256'd in `db.py`) is a light deterrent against casual snooping on a shared link, not real auth. Don't treat it as one.
- **Schema migration is automatic and runs on every startup** (`db._migrate()` in `db.py`). It detects the old singleton-table shape (`goals`/`profile`/`meal_plan` keyed by a hardcoded `id=1`, `entries` with no `user_id`) and folds it into a new "Aleks" user account so existing data survives. This is idempotent — safe to run against an already-migrated DB (it's a no-op) — but if you ever change the `users`/`goals`/`profile`/`meal_plan`/`entries` shape again, you'll need equivalent migration logic, not just an edit to `schema.sql` (which only fires `CREATE TABLE IF NOT EXISTS`, so it never touches existing tables).
- i18n: `frontend/i18n.js` holds the EN/BG dictionary and the `t(key, vars)` / `applyStaticTranslations()` helpers. Static markup uses `data-i18n` / `data-i18n-ph` attributes; anything rendered dynamically in `app.js` (entries, meal plan cards, history) calls `t()` directly in the template string — don't forget the JS-rendered paths when adding new UI text, `data-i18n` alone won't catch them. AI-generated text (vision item names, meal plan content) is translated server-side by passing `lang` through to `vision.py`/`meal_plan.py`, not client-side. Default language is Bulgarian (`currentLang()` falls back to `"bg"`, not `"en"`) — `t()` must call `currentLang()` rather than re-reading `localStorage` itself, or the two silently drift (this happened once already).
- `applyStaticTranslations()` must run before the user-gate screen is shown, not just after a profile is picked — the gate has its own `data-i18n` elements and its own language toggle (`langBtnGate`, separate button/id from the in-app `langBtn`, both call the same `toggleLanguage()`).
- **Per-item macros**: `vision.py` now returns `calories`/`protein_g`/`carbs_g`/`fat_g` per item, not just `name`/`est_grams`. `PUT /api/entries/{id}/portions` rescales an item proportionally when its grams are corrected (`new_value * (new_grams/old_grams)`), then re-sums the entry totals. Entries logged before this change lack per-item macros — `_rescale_items()` in `main.py` falls back to splitting the entry's stored totals by each item's share of total grams; that fallback must read the **entry row's** `total_calories`/etc, not sum a per-item `calories` field that doesn't exist on legacy items (would silently zero out).
- **Auth is still just a claimed `X-User-Id` header, not a session token** — PIN verification happens once client-side at profile-switch time and is never re-checked server-side per request. `PUT /api/users/me/pin` re-verifies the old PIN before allowing a change, but that's the only place. This is deliberate (see the multi-user gotcha above) — don't "fix" it into real auth without being asked, it changes the whole trust model.
- **Forgotten PINs have no in-app self-service reset.** By design — the user asked for "change with old PIN" in-app, and "ask me" (Aleks, DB owner) as the fallback for a forgotten one. If that changes, it's a product decision, not a bug to silently patch.
- **`max_tokens` on `vision.py`/`meal_plan.py` needs headroom for Bulgarian.** Cyrillic JSON output runs longer than the English equivalent; the original 2048/3072 values truncated mid-string on real Bulgarian meal plans and crashed with an unhandled `JSONDecodeError` (500, not a clean error) — this actually happened in production once. Both files now also check `stop_reason == "max_tokens"` and catch `JSONDecodeError` explicitly, converting either into a `RuntimeError` that `main.py` turns into a clean 502. Don't let a bare `json.loads()` on model output go unguarded again.
- **Edit-entry modal is grams-first.** Photo entries show per-item grams inputs; hitting Save recalculates calories/macros from whatever grams are currently in the fields (via `/portions`) and saves in one step — there's no separate "recalculate" button anymore, that was the UX complaint that led to this. The 4 raw number fields live behind a collapsed `<details id="editAdvancedDetails">`; if it's open, those manual values overwrite the grams-based recalc (manual intentionally wins). For manual-source entries (no grams to correct), that details section is auto-opened instead, since it's the only edit path available.
- `t()` must never re-read `localStorage` itself — always go through `currentLang()`. This has already caused one bug (English leaking into the Bulgarian-default UI) from a copy-pasted `|| "en"` fallback that only got fixed in one of the two places.
