# Calorie Scanner — gotchas

- Backend and frontend are one FastAPI app: `backend/main.py` serves the API under `/api/*` and mounts `frontend/` as static files at `/`. There is no separate frontend server or build step.
- Vision calls go through `backend/vision.py`, model `claude-sonnet-5-5` (see below for why not Opus, and why 5.5 over 5), using `output_config.format` (json_schema) — the response is guaranteed valid JSON, no prompt-parsing fallback needed. `coach.py` and `meal_plan.py` also use `claude-sonnet-5`. If Anthropic ever deprecates it, only these `MODEL` strings need to change.
- **Model is `claude-sonnet-5`, not Opus — a deliberate cost decision, made after real A/B testing, not a default.** Ran the same real meal photos through both models plus an independent third opinion (Gemini) as a sanity check. Opus was consistently 7-15% higher than Sonnet on normal single-portion photos, and wildly higher (3115 vs 1622 kcal) on one ambiguous shared-dish photo — but Gemini's independent numbers landed *below* both, closer to Sonnet's, and Sonnet's fat-gram estimates specifically tracked Gemini far more closely than Opus's did. So "Opus is more accurate" wasn't actually supported by the evidence — Sonnet + tighter prompting was the better cost/accuracy tradeoff, not a compromise. **Don't add `temperature`** to any of these three `messages.create()` calls — Sonnet 5 also rejects it, same as Opus did.
- **Three real prompt bugs were found and fixed via this same A/B testing** (`vision.py`'s `SYSTEM_PROMPT`), each backed by a before/after re-test on the exact photo that exposed it: (1) **SERVING SIZE FOR SHARED DISHES** — a photo of a family-style tray of ~18 meatballs was getting sized as if the whole tray were one meal (3115/1622 kcal); the fix explicitly instructs estimating one typical individual serving (~300-450g) unless the photo is unambiguously already-plated or a user note says otherwise — re-test dropped it to 630 kcal, in line with Gemini's ~780. (2) **PLAUSIBILITY CHECK** — breaded fried chicken was getting assigned 70g protein for 280g of food, physically impossible for any real food (even pure meat tops out ~20-25g protein/100g, and breading dilutes further); the fix adds an explicit density sanity-check instruction — re-test dropped it to 34.6g, matching Gemini's 35g almost exactly. (3) **ITEM INTEGRITY** — the model occasionally emitted a zero-gram/zero-calorie placeholder "item" that was really just a note-to-self, not real food; the fix explicitly forbids non-food placeholder entries. If a future mis-measurement report doesn't match one of these three known patterns, don't assume prompting alone will fix it — re-run the same real-photo-before/after methodology (see git history around this note for the exact test scripts) before changing the prompt blind.
- **Cost optimizations in `vision.py`** (added after real credit-usage pressure): (1) the system prompt is split into a `cache_control: ephemeral`-tagged static block (`SYSTEM_PROMPT`) plus a tiny uncached language-name suffix, so the cache is shared across English and Bulgarian calls — confirmed via `response.usage.cache_read_input_tokens` in testing (90% cheaper on a cache hit). (2) `_optimize_image()` downscales any image over `MAX_IMAGE_PIXELS` (~1.15MP, Anthropic's own documented quality-plateau point) before it's sent to the API, re-encoding as JPEG — this only touches the copy sent to Claude, never the original file on disk, and leaves already-small images byte-identical. Don't lower `MAX_IMAGE_PIXELS` further or add aggressive JPEG compression without checking against real mis-measurement reports — this app's whole prompt-tuning history (bone mass, portion anchors, dedup) depends on the model actually being able to see fine detail.
- `ANTHROPIC_API_KEY` lives in `backend/.env` (gitignored). Never commit it.
- DB path and uploads dir are overridable via `CALORIE_DB_PATH` / `CALORIE_UPLOADS_DIR` env vars — used for Render's persistent disk and for test isolation. Don't hardcode paths in `db.py` or `main.py`.
- SQLite file and uploaded photos are gitignored — they're runtime data, not source.
- The service worker (`frontend/sw.js`) explicitly skips caching anything under `/api/` or `/uploads/` — cache-first there would show stale meal data or serve a 404 for a new photo. If you add new API routes, they're already excluded by prefix, no sw.js change needed.
- iOS does not read `manifest.json` for install — the `<meta name="apple-mobile-web-app-*">` tags and `apple-touch-icon` link in `index.html` are load-bearing for iOS home-screen install, not decorative.
- `est_grams` is `None`/`null` for manually-logged entries (no photo to estimate portions from) — the frontend must not assume it's always a number.
- **Bump `CACHE_NAME` in `frontend/sw.js` on every frontend change.** The service worker only re-checks its own script for byte changes; if `sw.js` is byte-identical to what's already installed, the browser never notices anything else changed. `app.js` and `style.css` are served network-first (fall back to cache offline) specifically so an installed PWA doesn't get stuck on stale UI — don't revert that to cache-first without a strong reason.
- `nutrition.py` and `meal_plan.py` are separate from `vision.py` on purpose — same Claude Opus 5 model, but text-only (no image), structured JSON output via `output_config.format`. `nutrition.py` is pure arithmetic (Mifflin-St Jeor), no API call.
- Profile fields can be `NULL` (nothing filled in yet) — `/api/goals/suggested` requires all of them and 400s otherwise; don't assume `db.get_profile()` returns a fully populated row.
- **Multi-user**: every table except `users` is keyed by `user_id`. Who the caller is comes ONLY from the server-side session (cookie `cs_session`, see the Sessions bullet) — `main.current_user_id` depends on `current_session`. A numeric profile id is only used to *choose* a profile at the sign-in screen (`POST /api/session {user_id, pin?}`); it is never proof of access, and the old `X-User-Id` header is ignored entirely (a test fails if that ever comes back).
- **Schema migration is automatic and runs on every startup** (`db._migrate()` in `db.py`). It detects the old singleton-table shape (`goals`/`profile`/`meal_plan` keyed by a hardcoded `id=1`, `entries` with no `user_id`) and folds it into a new "Aleks" user account so existing data survives. This is idempotent — safe to run against an already-migrated DB (it's a no-op) — but if you ever change the `users`/`goals`/`profile`/`meal_plan`/`entries` shape again, you'll need equivalent migration logic, not just an edit to `schema.sql` (which only fires `CREATE TABLE IF NOT EXISTS`, so it never touches existing tables).
- i18n: `frontend/i18n.js` holds the EN/BG dictionary and the `t(key, vars)` / `applyStaticTranslations()` helpers. Static markup uses `data-i18n` / `data-i18n-ph` attributes; anything rendered dynamically in `app.js` (entries, meal plan cards, history) calls `t()` directly in the template string — don't forget the JS-rendered paths when adding new UI text, `data-i18n` alone won't catch them. AI-generated text (vision item names, meal plan content) is translated server-side by passing `lang` through to `vision.py`/`meal_plan.py`, not client-side. Default language is Bulgarian (`currentLang()` falls back to `"bg"`, not `"en"`) — `t()` must call `currentLang()` rather than re-reading `localStorage` itself, or the two silently drift (this happened once already).
- `applyStaticTranslations()` must run before the user-gate screen is shown, not just after a profile is picked — the gate has its own `data-i18n` elements and its own language toggle (`langBtnGate`, separate button/id from the in-app `langBtn`, both call the same `toggleLanguage()`).
- **Per-item macros**: `vision.py` now returns `calories`/`protein_g`/`carbs_g`/`fat_g` per item, not just `name`/`est_grams`. `PUT /api/entries/{id}/portions` rescales an item proportionally when its grams are corrected (`new_value * (new_grams/old_grams)`), then re-sums the entry totals. Entries logged before this change lack per-item macros — `_rescale_items()` in `main.py` falls back to splitting the entry's stored totals by each item's share of total grams; that fallback must read the **entry row's** `total_calories`/etc, not sum a per-item `calories` field that doesn't exist on legacy items (would silently zero out).
- **Sessions (replaced the claimed-`X-User-Id` scheme).** `auth.py` + `sessions` table. The browser holds one random token in an HttpOnly, SameSite=Strict cookie (`Secure` whenever the browser used https, detected via `X-Forwarded-Proto` because Coolify's proxy hands the app plain http); only its SHA-256 is stored. Idle expiry 30 days (sliding, last-use written at most every 10 min), absolute cap 90 days. Every state-changing request also needs the per-session CSRF token in `X-CSRF-Token` (returned by `GET`/`POST /api/session`, kept in JS memory only) AND a same-origin `Origin` if one is sent (middleware in `main.py`). Signing in as another profile destroys the old session; changing a PIN signs out the profile's other sessions; deleting a profile deletes its sessions. A profile **without** a PIN still opens with one explicit tap (deliberate; it can't be locked). PIN profiles lock for 15 minutes after 5 consecutive wrong PINs (`users.pin_failed_count/pin_locked_until`; the counter is committed *before* the 401/429 is raised — raising inside a `with db.get_conn()` would roll it back, don't restructure that). Known limitation: because ids are public, anyone can lock a PIN profile for 15 minutes by guessing wrong; that is the price of an online lockout on a 4-digit PIN. Tests move the clock via `auth.now`.
- **PIN storage**: new/changed PINs are salted PBKDF2-SHA256 (`pbkdf2_sha256$iters$salt$hash`). Old unsalted sha256 PINs keep working and are rewritten to the new format only after the same PIN verified (`auth.check_pin_with_lockout`) — never at startup, never on a wrong PIN. A 4-digit PIN is brute-forceable offline whatever the hash; the lockout is the real defence.
- **`GET /uploads/{file}` requires a session and checks that an entry of the signed-in profile references the file, on every request** (`db.user_owns_upload`). Responses are `private, no-cache`; all `/api/*` responses are `no-store`. Nothing else serves the uploads directory (the static mount covers `frontend/` only; `.dockerignore` keeps local data out of images). `<img src="/uploads/...">` works because the cookie rides along. Unknown/foreign/orphan files all return the same 404.
- **Writes are validated on the server** (`validation.py`, 422 with `{code, field, min, max}`): height 100–250 cm, weight 30–300 kg, age 10–100, goal calories 1–10000, entry calories 0–10000, macros 0–2000 g, water goal 500–10000 ml, water *operation* ±5000 ml (nonzero; `db.add_water` still clamps so a day's total never goes below 0), body composition > 0 and ≤ weigh-in weight, water % in (0,100]. These are typo/unit-mix-up guards, not nutrition advice, and apply to writes only — values already stored outside them stay readable and are not rejected by unrelated partial updates. Don't re-validate on read.
- **One business operation = one request = one transaction.** `PUT /api/entries/{id}` takes optional `items` (grams) AND the detail fields together (explicit numbers still win over the grams recalculation); `POST /api/goals/apply` saves profile + targets together; the old `PUT /api/entries/{id}/portions` remains for compatibility. Fault-injection tests run the real write and then raise, proving the rollback. `POST /api/weight` returns the entry plus the current `goals` and `goals_changed`; the page re-renders Today's targets from that (changed or not).
- **Frontend networking rules** (`frontend/api.js`, covered by `node --test tests/js/*.test.js`): all writes go through `write()` in `app.js` — single-flight per button (a second tap while the first is in flight is ignored), the sheet/fields are only cleared after a 2xx, failures keep the draft and say why, and **a write is never retried automatically** (a dropped connection is reported as "unclear whether saved"; repeating it could double-log a meal). A 401 / stale-CSRF opens the sign-in screen *over* the app (unsaved input survives); same profile resumes, a different profile triggers `location.reload()` so none of the previous profile's data, photos or drafts remain. Never store a claimed user id or any token in `localStorage`. **A read-then-write handler is guarded as a whole**: applying a suggestion (a delta on the CURRENT targets) runs its `GET /api/goals` *and* its `PUT` inside one `guard(GOALS_WRITE, …)` (using `sendWrite`, the unguarded half of `write()`); every change to the targets shares that key, so a second tap cannot repeat the read — a guard that starts after the read applied +150 twice (2500→2650→2800). `tests/js/app_handlers.test.js` loads the real `app.js` into a `vm` with a fake DOM (`tests/js/helpers/app_harness.js`) and drives the actual handlers with held requests; `CS_APP_SOURCE=<file>` runs the same tests against another copy of `app.js` to prove they fail on the old code.
- **Units**: the Plan form stores/sends metric only. `state.canon` holds the canonical cm/kg; imperial fields are derived from it (`units.js`) and only replace it when the user types — flipping units repeatedly cannot accumulate rounding. Don't convert displayed values back into canonical ones. Editing a field replaces ONLY the canonical value behind that field (`CSUnits.canonAfterEdit`): the other one is never re-derived from its rounded imperial display (80 kg shows as 176.4 lb, which converts back to 80.01 kg — editing the inches used to change the weight).
- **Backups and "nothing was lost" checks** (`backend/tools/`, stdlib only; the folder ships in the image so it can run in the Coolify terminal): `backup.py create|verify|restore` (SQLite online-backup API + the uploads photos + a SHA-256 manifest; `restore` refuses to overwrite and ignores the app's env paths) and `db_snapshot.py snapshot|compare` (per-row hashes; hash-only by default so no personal values). Copying the `.db` file with cp is NOT a safe backup while the app is running. A verified backup of the production DB **and** `/data/uploads` must exist before any deploy that touches the schema; none is scheduled automatically (an open item). **`verify` fails closed**: a mandatory database member, a validated manifest (structure, safe member paths, hashes, sizes), and — exit code 2, `INCOMPLETE ARCHIVE`, never `VERIFIED` — any photo that an entry points to but the archive lacks (the database inside the archive decides, not the manifest's own claim); `restore` refuses an incomplete archive without `--allow-incomplete`; `create` refuses a missing uploads directory; both refuse a database whose photo references cannot be checked (no `entries` table or no `image_path`/`image_path2` column is an error, never "no photos"). `db_snapshot.py compare` compares every old cell by primary key (per-cell hashes, no values), so added columns or `--allow-changed` can never hide a changed value; new tables/columns must be named (`--allow-new-table`, `--allow-new-column`) and a snapshot without cell hashes is rejected. `backup.py fingerprint`/`compare-fingerprint` prove a quiet window (SHA-256 of the db file and every photo, before and after). The server procedure is in `backend/tools/SERVER_BACKUP.md`: `archive_window.sh` stops the app container for the few seconds of the snapshot (equal fingerprints only compare end states, they cannot prove there were no writes in between), restarts it from a trap on every exit path, and keeps every attempt in its own directory, failed ones included.
- **Tests**: `cd backend && .venv/Scripts/python -m unittest discover -s tests -t .` (no extra dependencies; per-test temp DB/uploads, movable clock, AI clients that raise if a test reaches a paid call) and `node --test tests/js/*.test.js`. `backend/tests/ui_server.py` serves the real app on synthetic people with stubbed AI and failure/delay hooks under `/api/__test/*` for driving the UI in a browser — keep hooks under `/api/` because the service worker caches other paths and will happily serve a stale hook answer. `test_nutrition_unchanged.py` pins the nutrition formulas/thresholds on synthetic inputs; any change there must be deliberate. Migration safety is covered by `test_preservation.py` (old-schema DB from `tests/fixtures/schema_pre_stage1.sql`). Needs `pip install -r backend/requirements-dev.txt` (adds `httpx` for the test client) and Node 18+; the JS suite is `node --test tests/js/*.test.js` (a directory argument does not work on Node 24).
- **Stage 2 Today screen** (`index.html` + `renderTotals`/`renderEntries`/`renderWater`): kcal-left number + a pill bar (`#calBarFill`, no ring), macros with units, meal rows with photos (tap a row = open the editor; favourite and delete live IN the editor now, `#editFavoriteBtn`/`#editDeleteBtn`, delete still asks first), water in litres with a bar, energy dots, diary row. Meals are oldest-first. Photo / Manual / Quick Add all live in ONE panel (`#addFoodModal`, opened by the fixed `#addFoodBtn` dock, which is visible without scrolling at 390x844 and sits above the nav; it only exists on the Today tab and hides while a text field is focused on a short viewport). Their own handlers are unchanged; the panel just closes once one is chosen. The header is the screen title + date + avatar (= switch profile, **asks first**) + settings; language, What's New, install, theme and style moved into the Settings sheet (same element ids). The History tab is labelled "Progress" (`data-tab="history"` is unchanged).
- **Dialogs get their behaviour from one observer, not per call site.** Every `.modal-backdrop` is given `role=dialog`, `aria-modal` and a title label at load; a `MutationObserver` on the `hidden` class moves focus into the sheet on open (the sheet itself, so no keyboard pops up), makes `#appRoot` inert, restores focus on close (to the opener, else the Add-food button), traps Tab, and closes on Esc by clicking the sheet's own Close/Cancel button (`DIALOG_CLOSE_BUTTON`). A new modal needs its id in that map plus `<div class="sheet-handle">` and an `attachSheetDrag(...)` call. File inputs (`#photoInput`, `#photoInput2`) must stay OUTSIDE `#appRoot` — an inert page would block the picker. `visualViewport` feeds `--vvh`/`--vvt` so sheets stay inside the visible area when a keyboard is up (real iOS/Android keyboards were NOT tested, only a short emulated viewport).
- **Roman Legion is presentation only** (`frontend/legion.js`, wired at the end of `app.js`). The portrait is a vector PLACEHOLDER drawn in code (`portraitSvg()`, marked in the source) — swap it for final art without touching the logic. Lines, moods and the reaction state machine are local and deterministic (no network, no storage, no AI, no `Math.random`; a test greps `legion.js` for that). The three required reactions are **approve** (also shown for real, right after a meal was actually logged, never marked demo), **remind** and **demand**. `remind`/`demand` need a real meal schedule and a real eating time, which do NOT exist yet (an upload time is not proof of when something was eaten), so today they are reachable ONLY through the dashed, labelled DEMO panel (it writes nothing; can be hidden in Settings). The hooks are ready: `CSLegion.reaction(kind, lang, n, {time})` and `CSLegion.chipsHtml({nextMeal, lastLog})` — wire them to real data later instead of the demo buttons.
- **JS tests grew**: `look.js`/contrast/tokens in `tests/js/appearance.test.js`, the centurion in `tests/js/legion.test.js`, and the Today screen / Add-food panel / editor actions / demo isolation through the real `app.js` in `tests/js/today_screen.test.js`. The fake DOM in `tests/js/helpers/app_harness.js` now has a real `classList`, `setAttribute`, `click()`, escaping `textContent`, a `confirm` hook and a seedable `localStorage` (`loadApp({ storage, confirm, route })`). `backend/tests/ui_server.py` seeds an invented "Demo" profile with drawn (not real) food images for screenshots.
- **Forgotten PINs have no in-app self-service reset.** By design — the user asked for "change with old PIN" in-app, and "ask me" (Aleks, DB owner) as the fallback for a forgotten one. If that changes, it's a product decision, not a bug to silently patch.
- **`max_tokens` on `vision.py`/`meal_plan.py` needs headroom for Bulgarian.** Cyrillic JSON output runs longer than the English equivalent; the original 2048/3072 values truncated mid-string on real Bulgarian meal plans and crashed with an unhandled `JSONDecodeError` (500, not a clean error) — this actually happened in production once. Both files now also check `stop_reason == "max_tokens"` and catch `JSONDecodeError` explicitly, converting either into a `RuntimeError` that `main.py` turns into a clean 502. Don't let a bare `json.loads()` on model output go unguarded again.
- **Edit-entry modal is grams-first.** Photo entries show per-item grams inputs; hitting Save recalculates calories/macros from whatever grams are currently in the fields (via `/portions`) and saves in one step — there's no separate "recalculate" button anymore, that was the UX complaint that led to this. The 4 raw number fields live behind a collapsed `<details id="editAdvancedDetails">`; if it's open, those manual values overwrite the grams-based recalc (manual intentionally wins). For manual-source entries (no grams to correct), that details section is auto-opened instead, since it's the only edit path available.
- `t()` must never re-read `localStorage` itself — always go through `currentLang()`. This has already caused one bug (English leaking into the Bulgarian-default UI) from a copy-pasted `|| "en"` fallback that only got fixed in one of the two places.
- **Timezone**: `tzutil.py` centralizes on `Europe/Sofia` (via `zoneinfo` + the `tzdata` package — Windows and some minimal Linux images don't ship an IANA tz database, so `tzdata` in `requirements.txt` is load-bearing, not decorative). Every `created_at`/"today" boundary goes through `tzutil.now_local_naive()` / `tzutil.today_local()` — never call bare `datetime.now()` or `date.today()` in this backend again, that reintroduces the original bug (server ran on UTC, day boundary was hours off from Sofia).
- **Energy score is a quality rating, not a quantity one.** It's per-entry (not per-item), comes straight from `vision.py`'s `energy_score` field, and `_rescale_items()` in `main.py` never touches it — correcting grams changes calories/macros but must never change how "good" the food is. Manual entries have no score (`energy_score` stays `NULL`), and `_totals()` averages only over entries that have one — don't let a `None` silently become `0` and drag the average down.
- **Second photo angle**: `vision.py`'s `analyze_meal_photo(images, lang)` now takes a *list* of `(bytes, media_type)` tuples (1 or 2), not a single image — both get sent as separate image blocks in the same Claude message. `entries.image_path2` is nullable; cleanup paths (`_remove_upload`, delete-user cascade, reset-today) all need to handle both `image_path` and `image_path2`, not just the first.
- **Coach tip and meal plan are both cached server-side per day** (`daily_tip` keyed by `(user_id, tip_date)`, similar to `meal_plan`'s per-user row) specifically so the frontend's "get tip" button doesn't fire a paid API call on every page load — only on explicit user action. Don't wire tip-fetching into automatic page load without keeping that in mind.
- **What's New** (`frontend/whatsnew.js`): bump `CURRENT_APP_VERSION` and add a new `WHATS_NEW` entry (both `en` and `bg` arrays) whenever you ship a user-facing feature worth announcing — it's shown automatically once per version bump (tracked via `localStorage.whatsNewSeenVersion`), skipped entirely for brand-new profiles (nothing to announce to someone who's never seen the old version).
- **Vision prompt accuracy rules** (`vision.py`'s `SYSTEM_PROMPT`), added after real mis-measurements were reported: (1) multi-image dedup — two angles of one meal must merge into one item list, never double-counted; (2) edible-mass-only — bone-in meat (chicken legs/wings/ribs) must have bone mass (~30-35%) subtracted before calories/macros, and the item name should say "edible meat ~Xg"; (3) portion anchors over package defaults — estimate the visible quantity, don't default to a manufacturer's standard serving size when the photo clearly shows more/less; (4) user text notes are applied once to exactly what they describe (e.g. "add 3 slices of bread" = one new item) and must never cause the rest of the plate to be re-estimated differently from what the photo shows. If future mis-measurement reports come in, tighten rules here first before touching anything else — this is the single place vision accuracy is tuned.
- **Weight tracking**: `weight_log(id, user_id, logged_at, weight_kg)` is append-only history; `profile.weight_kg` is kept as "most recent" and gets overwritten by `db.add_weight_entry()` every time a new weigh-in is logged, so the two never drift. `GET /api/weight` returns newest-first — the frontend's delta coloring in `loadWeightLog()` compares each row to `entries[i+1]` (the next-older one) and colors it "good" only relative to the profile's `goal_type` (lose wants negative deltas, gain wants positive) — don't hardcode "down is good".
- **Favorites**: a snapshot copy (`favorites` table), not a live reference to the source entry — deleting or editing the original entry never touches a favorite made from it, and vice versa. `POST /api/favorites/{id}/log` inserts a normal `entries` row with `source="favorite"` and `confidence="manual"`; if the favorite came from a photo-analyzed entry, its `items_json` still has per-item `est_grams`/macros, so the edit modal's grams-correction UI works on it exactly like a fresh photo entry.
- **Meal-plan "Log this"** reuses the existing `/api/log-manual` endpoint (no new endpoint) — `app.js`'s `logPlanMeal()` reads macros straight from `state.lastPlan.meals[idx]`, which is only populated by `renderMealPlan()`; don't call it without a plan rendered first. `switchTab()` in `app.js` is the one shared helper for changing tabs from code (used here and by `logFavorite()`) — route new "jump to Today after doing X" flows through it instead of duplicating the tab-toggle DOM logic.
- **The app pivoted from general weight-loss tracking to a hardgainer/surplus-focused tool**, personalized for Aleks — but it's still multi-user (Ani uses `"lose"`/`"maintain"`), so nothing here is allowed to assume everyone is bulking. `ALLOWED_GOAL_TYPE` still has all three values; `DEFAULT_RATE_KG_PER_WEEK["gain"]` is `0.4` (was `0.25`) to match a ~400kcal/day surplus.
- **Adaptive TDEE engine** (`nutrition.py`'s `ewma_weight_trend()` / `calculate_adaptive_tdee()`, `GET /api/tdee/adaptive` in `main.py`) is a separate, additive path from the static Mifflin-St Jeor `calculate_targets()` — it computes a "Real TDEE" from actual logged intake vs. an EWMA-smoothed weight trend (alpha=0.2, ~9-day half-life), not a formula, and only reports a number once there's `ADAPTIVE_MIN_ELAPSED_DAYS` (10) days of weigh-in history AND `ADAPTIVE_MIN_INTAKE_COVERAGE` (70%) of days logged; otherwise `insufficient_data: true` with a machine-readable `reason`, never a nonsense number from sparse data. It's computed on demand (button tap), never a cron — there's no always-on process now that hosting's paused. Applying it only changes `goals.calories`/`carbs_g` (via the same `PUT /api/goals` used everywhere else, protein/fat floors preserved) — it never touches `profile`.
- **EWMA warmup matters**: `ADAPTIVE_LOOKBACK_DAYS` (21) is deliberately wider than the 14-day scored window so the EWMA isn't cold-started right where the analysis begins — this bit us once already in the fat-mass adjustment rule (see below), where restricting the fat series to the scored window *before* smoothing systematically understated the fat trend. Any new EWMA-based series must get the same wider lookback before being sliced down to the scored window, not smoothed only within it.
- **Scale-driven adjustment suggestions** (`nutrition._evaluate_adjustment_rules()`, folded into `calculate_adaptive_tdee()`'s return under `suggestions`, not a separate endpoint) reuse the same window: `under_fueled` fires when the 14-day weight delta is under 0.5kg (suggest +200kcal), `fat_spike` fires when EWMA-smoothed `fat_mass_kg` growth accounts for over 70% of total weight gain (suggest -100kcal) — the fat rule only fires when the (lookback-warmed) fat series actually reaches back to the window's start; sparse/absent scale data means it silently doesn't fire, never an error. Applying a suggestion is a *relative* delta on top of current `goals.calories` (fetched fresh, not cached) — different from the main Adaptive TDEE apply, which sets an absolute target.
- **`weight_log` carries optional body-composition columns** (`fat_mass_kg`, `muscle_mass_kg`, `water_pct`, all nullable) — manual entry only (via the History tab's collapsed "+ Add body composition" fields), no smart-scale hardware/API sync exists or is planned without a specific device/vendor being named. The Gemini spec's Deload/CNS-fatigue rule (cross-referencing scale trend against Hevy workout performance) was deliberately excluded — this app has no Hevy integration, and that's real third-party OAuth work for its own round, not something to stub here.
- **Goal-aware visual language is conditional on `profile.goal_type`, never global.** `app.js`'s `applyGoalAwareClass()` (used by `renderTotals()`'s calorie bar and `setMacro()`'s macro bars) only flips "over target = good (`.over-good`, the `--success` colour)" / "under target = warning (`.under-warning`, `--warning`)" when `state.goalType === "gain"` (fetched fresh in `loadToday()` alongside `/api/today`); for `"lose"`/`"maintain"`/unset over = `--danger` (`.over`) and there is never an under-target warning. This app is multi-user — a `"lose"`-goal user (Ani) must never see "you went over, good job" styling. The state classes recolour only the calorie bar; a macro bar keeps its own colour (protein blue, carbs green, fat gold) in every state and only its NUMBER takes the state colour. Success, warning and danger are their own tokens and must never reuse a macro colour (`tests/js/appearance.test.js` fails if they do).
- **Appearance = two INDEPENDENT settings, both per device.** `frontend/look.js` (loaded in `<head>`, so no flash) owns `theme` (`system | light | dark`, stored under the old `theme` key) and `mode` (`normal | roman`, stored under `lookMode`) and writes them as `data-theme` / `data-mode` on `<html>`; `style.css` keeps ALL colour tokens in four blocks (normal/light warm, normal/dark graphite, roman/light parchment+burgundy, roman/dark burgundy night+bronze) and everything else reads tokens — never hard-code a colour in a rule, add a token to all four blocks. `tests/js/appearance.test.js` parses those blocks and enforces WCAG contrast (text 4.5:1, bars/focus 3:1, button text 4.5:1 along the whole gradient), identical macro colours in both styles, and distinct success/warning/danger. The light-theme gold is a deep antique gold (`#B87F00`) on purpose: a brighter gold fails 3:1 on white/parchment. `prefers-reduced-motion` switches every animation/transition off (`html.reduce-motion` is the same rule for a manual switch).
- **Bottom-sheet drag-to-dismiss** (`app.js`'s `attachSheetDrag(sheetEl, closeFn)`) is wired once per modal at script-load time, not per-open — it finds `.sheet-handle` (must be the first child of `.modal-sheet`) and calls `closeFn` on a big-enough drag or fast-enough flick. Any new modal needs both the `<div class="sheet-handle"></div>` markup and its own `attachSheetDrag(...)` call near the bottom of `app.js`, or it just won't be draggable (fails silently, no error — the function no-ops if `.sheet-handle` isn't found).
- **Scale screenshot OCR** (`vision.parse_scale_screenshot()`, `POST /api/weight/scan` in `main.py`) reads a BIA smart-scale app screenshot (Huawei/Honor Health etc.) and returns `weight_kg` plus optional `body_fat_pct`/`fat_mass_kg`/`skeletal_muscle_kg`/`bmr_kcal`/`body_water_pct`/`protein_pct` — every field except `weight_kg` is nullable in the schema (`{"type": ["number", "null"]}`) since not every screenshot shows every metric, and the model must never fabricate one that isn't visible. This endpoint **does not write to the DB or save the image** — it's a pure OCR-to-JSON step; the frontend (`scanScaleBtn`/`scaleScanInput` in `app.js`) prefills the existing weight/composition inputs and the user still presses the existing "Log" button (`POST /api/weight`) to actually persist, same as any other manually-reviewed entry. Only `fat_mass_kg`/`skeletal_muscle_kg`→`muscle_mass_kg`/`body_water_pct`→`water_pct` map onto real `weight_log` columns; `body_fat_pct`/`bmr_kcal`/`protein_pct` have no column to live in (out of scope to add for this round) and are only surfaced as read-only info text (`#scaleScanInfo`) — don't wire them into a save call, there's nowhere for them to go yet.
- **Autonomous analyst engine** (`main.py`'s `evaluate_and_auto_adjust_user()`) runs synchronously after every `POST /api/weight` — not after `POST /api/weight/scan`, since scan is pure OCR and never persists a weigh-in; only the actual save triggers evaluation. It reuses `nutrition.calculate_adaptive_tdee()`/`_evaluate_adjustment_rules()` (same engine the manual "Recalculate From My Data" button on the Plan tab calls) and, unless one of three gates stops it, writes straight to `goals` with no user confirmation: (1) `insufficient_data` → does nothing, not even a log row; (2) combined suggestion delta under `AUTO_ADJUST_MIN_COMMIT_KCAL` (50) → logs a no-op; (3) `AUTO_ADJUST_COOLDOWN_DAYS` (7) since the last row in `analyst_logs` that actually changed calories → logs a no-op explaining the skip; (4) `goals.auto_apply_targets` is 0 → logs what it *would* have done but doesn't touch goals. Every path except the true insufficient-data case writes an `analyst_logs` row, so the Analyst Feed always has something to say when it's evaluated at all. This is a deliberate reversal of this app's long-standing "always requires a tap" pattern — auto-apply defaults **on**, per explicit user decision, not a default this codebase would pick on its own.
- **Adjustment-rule thresholds changed** (`nutrition.py`): under-fueled/on-track are now velocity-based (`ADJUSTMENT_UNDER_FUELED_MIN_VELOCITY_KG_WEEK` 0.2 kg/week → +150kcal; `ADJUSTMENT_SWEET_SPOT_MIN/MAX_KG_WEEK` 0.3–0.5 kg/week → explicit `on_track` no-op suggestion) rather than the old flat 0.5kg/14-day gain check, and fat-spike's ratio dropped from 0.7 to `ADJUSTMENT_FAT_SPIKE_RATIO` (0.65). A fat-spike suggestion now also carries `protein_floor_g` (135) and `prioritize_carbs: true` — applying it (auto or manual) must hold protein at that floor and cut **fat grams** (floored at `ADJUSTMENT_FAT_FLOOR_G`=40) rather than letting carbs absorb the delta; every other suggestion type keeps the original protein/fat-fixed, carbs-absorbs-delta behavior. `nutrition.apply_calorie_adjustment(goals, calorie_delta, prioritize_carbs)` is the one place this macro math lives — the manual suggestion-apply handler in `app.js` mirrors it by hand (JS can't import it), so a future threshold/formula change needs both places updated together.
- **`suggestions` can include `type: "on_track"` with `calorie_delta: 0`** — an explicit "nothing to do" signal, not silence, so both the autonomous engine and the manual Plan-tab UI can say *why* nothing changed. The manual UI renders it as an info line with no Apply/Ignore buttons (`renderAdaptiveTdee()` in `app.js`) — don't treat every entry in `suggestions` as actionable.
- **`analyst_logs`** (`id`, `user_id`, `created_at`, `old_calories`, `new_calories`, `reason_text`) is an append-only audit trail, read via `GET /api/analyst/logs`. `old_calories == new_calories` marks an informational/no-op row (evaluated, nothing committed) — the cooldown check (`db.get_last_committed_adjustment()`) specifically excludes these, only counting rows where a real change happened, so a string of no-op evaluations never blocks a future real one.
- **`goals.auto_apply_targets`** (nullable-free INTEGER, default 1) is the Settings toggle backing store — `PUT /api/settings/auto-apply-targets` is its own endpoint, deliberately separate from `PUT /api/goals` (same reasoning as PIN having its own endpoint: a different kind of change than the targets themselves). Toggling it off does not stop evaluation or logging, only the actual `goals` write.
- **Auto-adjustment has an adherence gate ("bridge to reality")**: `under_fueled` infers "raise the target" purely from weight velocity, which can't tell a target that's genuinely too low apart from one that just isn't being hit yet. `evaluate_and_auto_adjust_user()` compares `avg_daily_intake` (already computed by `calculate_adaptive_tdee`) against the *current* `goals.calories` — below `nutrition.ADJUSTMENT_ADHERENCE_GATE_PCT` (0.85), the under_fueled raise is excluded from `effective_suggestions`/`total_delta` (never auto-committed) and the row is marked with an `adherence_gap` finding instead, since silently raising an already-unhit number just makes the gap bigger. This gate applies **only** to `under_fueled` — `fat_spike` is left alone since it's driven by real scale-measured body-fat-mass change, which is true regardless of how well food logging tracks it. The manual "Recalculate From My Data" button on the Plan tab is unaffected by this gate (a human reviewing the number before tapping Apply is already the safety check) — only the silent autonomous path is tempered.
- **Multi-macro adherence, not just calories** (`nutrition.calculate_macro_adherence()`) — compares logged protein/carbs/fat, not only calories, against `goals` over the same window `calculate_adaptive_tdee` already scored, classifying each as `"under"`/`"on_target"`/`"over"` via `ADJUSTMENT_ADHERENCE_GATE_PCT` (0.85) and `ADJUSTMENT_ADHERENCE_OVER_PCT` (1.15). Only **calorie** adherence gates auto-commit behavior (the under_fueled bridge-to-reality check) — protein/carbs/fat adherence are informational/coaching signals only, surfaced as a `protein_gap` finding (fires independently of which weight-trend rule triggered, since under-eating protein undermines a gain phase even when total calories look fine) and as dietary-fat context attached to `fat_spike` findings when fat intake isn't on target. Don't add new auto-commit gates on carbs/fat without deliberately deciding to — the scope here was "make the data visible," not "add three more silent triggers." `main._daily_macro_totals()` (which `_daily_calorie_totals()` now wraps) is the one place daily intake gets bucketed by day for this — extend it, don't duplicate it, if another macro-level view is needed later.
- **`analyst_logs.reason_text` is deterministic and localized** (`main.py`'s `_ANALYST_MESSAGES` dict, `en`/`bg`) — always written, never skipped, and mirrors the i18n convention used elsewhere (don't add a third language without adding both a template set and threading `lang` through). **`analyst_logs.coach_note`** is the richer, AI-generated "coach" layer on top (`coach.generate_analyst_note()` in `coach.py`) — only generated for a noteworthy row (a real commit, a fat-spike, or an adherence gap) and rate-limited by `nutrition.COACH_NOTE_MIN_INTERVAL_DAYS` (3) *independently* of the 7-day auto-commit cooldown, since an adherence-gap finding can recur every single weigh-in and would otherwise call the API daily. The frontend (`loadAnalystFeed()` in `app.js`) shows `coach_note || reason_text` — never assume `coach_note` is populated. Since `evaluate_and_auto_adjust_user()` runs inside `POST /api/weight` (not a user-initiated request with an obvious language), the frontend now sends `lang: currentLang()` in that request's payload specifically so the coach note comes back in the right language — don't lose that field if `logWeightBtn`'s handler gets refactored.
- **Target Gap Recommender is goal-gated to `"gain"` only** (`app.js`'s `renderGapRecommender()`, Today tab) — same multi-user principle as the goal-aware visual language rule above, applied to a recommendation instead of a color: telling a `"lose"`/`"maintain"` user (Ani) to eat 600+ kcal of dense food because they're "under target" would actively undermine their goal, so this card is invisible outside `state.goalType === "gain"` regardless of how much of the daily calorie gap is open. The three options are a static curated list, not an AI call — no reason to spend API cost on food-combo math that doesn't need personalization.
- **All functional UI icons are inline SVG now, not emoji** — this covers the tab bar, header buttons (settings/switch-user/what's-new/install/theme), wellness labels, every button icon, and every dynamically-rendered icon in entries/favorites/weight-log/meal-plan (pin lock, energy badge, note marker, favorite/edit/delete actions, meal-time icons). Tab bar icons are styled via `.tab-btn svg`/`.tab-btn.active svg` in `style.css` (no `stroke`/`fill` attributes on the markup — CSS drives color so the dark/light theme tokens apply). Everywhere else, icons carry `stroke="currentColor" fill="none"` directly on the `<svg>` so they inherit whatever `color` the surrounding element already has (button text color, `--text-dim`, etc.) — no extra CSS needed per icon. Static markup in `index.html` has icons inline; `app.js` has a shared `ICON` object (top of the file) with the same icons as reusable strings for template literals — add new icons there rather than inlining raw SVG in a template string, so entries/favorites/weight-log/meal-plan stay visually consistent. **Explicitly left alone**: the 🍽 logo-mark (app branding/gate screen and header title) — that's covered by the earlier "no icon/name changes" instruction, not the emoji-icon sweep; ask before touching it. Decorative emoji in AI-generated text (coach tips, vision item names) and in `whatsnew.js` release-note bullets are also out of scope — this rule is about icons standing in for UI actions/state, not flavor text.
- **Days are unknown, not zero — the analyst only averages *complete* days.** `main._day_is_complete()` counts a day when it has `nutrition.COMPLETE_DAY_MIN_MEAL_TYPES` (3) distinct meal types, or the user marked it `complete` in `day_marks` (`PUT /api/days/{date}/mark`, `status: complete | skip | null`; `skip` always excludes). It's judged by meal types, deliberately **not** by calories — a calorie floor would hide genuine under-eating, which is exactly what the adherence gate exists to catch. `_daily_macro_totals()`/`_daily_calorie_totals()` take `marks` and filter to complete days by default, so the ADAPTIVE_MIN_INTAKE_COVERAGE check, `avg_daily_intake`, and macro adherence all run on trusted days only. Before this, one logged snack counted as a full 700 kcal day and produced false "you're eating far below target" findings. Every caller must pass `marks` (fetch with `db.get_day_marks`) — calling without it silently falls back to inferred-only. `/api/history` rows carry `status` (`complete|partial|skipped|empty`) + `mark`; the History tab shows empty days as "—" (not a 0 bar) and lets the user cycle partial → confirmed → skipped by tapping the chip; the Today tab has a "That's everything for today" button on partial days. The coach note gets a `tracking` block and is told never to read partial logging as under-eating.
- **Adjustment rules are goal-aware** (`_evaluate_adjustment_rules(..., goal_type)`, `calculate_adaptive_tdee(..., goal_type=)`). Only `"gain"` has the original `under_fueled`/`fat_spike`/velocity-sweet-spot logic. `"lose"` gets `lose_stalled` / `lose_too_fast` / `on_track`; `"maintain"` (and unset) gets `maintain_drift_up` / `maintain_drift_down` / `on_track`. The Real-TDEE buffer is per goal (`SURPLUS_BUFFER_BY_GOAL`: +400 / 0 / −500) — previously every user got +400, and a lose-goal user losing exactly as intended was told they were "under-fueled" and had +150 kcal auto-committed. **The silent auto-commit and the AI coach note are gain-only**: for lose/maintain, `evaluate_and_auto_adjust_user()` logs the deterministic finding with a `manual_only` line and leaves `goals` untouched; those suggestions are reviewed via the Plan tab's manual buttons. `on_track` suggestions now carry `range_min`/`range_max` instead of hardcoded gain-range constants.
- **Sonnet 5 "thinks" by default, and thinking tokens count against `max_tokens`.** Found the hard way: the analyst coach note (`coach.generate_analyst_note`) was set to 500 and raised `stop_reason == "max_tokens"` on real Bulgarian output — a ~200-token note used 450–1000+ tokens total. `evaluate_and_auto_adjust_user()` swallows that error by design, so in production it would have silently produced *no coach note ever*, with nothing in any log. Never size `max_tokens` from the visible output length; leave several times that, and test with a real call rather than a mocked coach. Current limits: coach note 4000, daily tip 2000, scale OCR 2048, vision 3072 (measured ~300 used), meal plan 6000.
- **Vision uses `claude-sonnet-5-5` (Sonnet 5.5); `coach.py`/`meal_plan.py` still use `claude-sonnet-5`.** Same price ($2/$10 per MTok), so the switch was decided purely on a real A/B: the same 5 photos x 3 runs per model with the production prompt. 5.5 was far more *repeatable* — run-to-run kcal spread 5-11% vs 6-22% for Sonnet 5 on 4 of 5 photos — and closer to the independent Gemini reference on the two dishes we have one for (shared-tray meatballs 704 vs 615 kcal against Gemini's ~780; sesame chicken protein a steady 36-38g vs Sonnet 5's 38/49/56 against Gemini's 35g — i.e. Sonnet 5 occasionally slipped back into the implausible-protein pattern the PLAUSIBILITY CHECK rule targets). It is also more willing to say `confidence: "low"` on ambiguous photos. Cost: it thinks more, ~+15% per call (~$0.0118 vs ~$0.0103, ~$1.41 vs ~$1.24/month at 4 meals/day). The text-only coach/meal-plan calls were not part of this test; move them only with their own evidence. `parse_scale_screenshot()` shares `vision.MODEL` and was not separately re-tested on 5.5.
- **Frontend files are served with `Cache-Control: no-cache`** (`main.NoCacheStaticFiles`). The app is currently reached over plain `http://` (Coolify's temporary sslip.io address), and service workers only register on HTTPS/localhost — so the "network-first `app.js`/`style.css`" freshness logic in `sw.js` does nothing there. Without any Cache-Control header the browser used heuristic caching (~10% of the file's age) and kept serving a stale `app.js`/`index.html` for days after a deploy; this actually happened (a user saw the pre-day-marks UI hours after deploy while the server was serving the new one — verify with `curl`, not the browser). When the app gets a real HTTPS domain the SW starts working, but keep `no-cache` anyway. Note it can't retroactively fix copies already cached by a browser — that needs a one-time cache clear.
